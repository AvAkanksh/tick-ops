**How to read the server columns.** ClickHouse and QuestDB are real servers (Docker, each pinned to the same number of cores) queried over HTTP, so their numbers include the network round-trip and decoding the result into Arrow in Python; DuckDB, Polars and pandas are in-process and pay none of that. For Q1, which returns one row per trade, that transfer is a large share of the server time. QuestDB's Q3 is an as-of-join rewrite: the direct range-join port is correct but exceeds QuestDB's 60 s query timeout at this scale (see `queries_questdb.py`).

### Scoped query — one symbol, one day

The far more common desk query is "pull one name for one day" — an as-of join scoped to a single symbol-day (**14112** result rows). The intuitive expectation is that `by_date_symbol` wins here by pruning to one file. At this scale it does not: a pruned scan is a few milliseconds on every layout, so the layouts land within a few ms of each other (fastest `sorted` 19 ms, slowest `single` 28 ms) and directory partitioning buys nothing measurable. The cost of `by_date_symbol` — one small file per symbol-day — only shows up as data grows. Timed from Parquet, median ms.

| Query | single | by_date | by_date_symbol | sorted |
|---|--:|--:|--:|--:|
| scoped as-of (1 symbol × 1 day) | 28 ms | 21 ms | 26 ms | 19 ms |

The scale-dependence is the migration lesson — see `scripts/run_partition_study.py` and `results/partition_study.md`, which sweep dataset size and show `by_date_symbol` getting *worse* as data grows (8x as many files as `by_date` at every size) while `sorted` (date partitions, symbol-clustered, statistics on) stays fastest.

### One-time in-memory load (paid once per session, then amortized)

The compute table above excludes this by design: a research session loads the working set once and runs many queries against it. Shown so it is not hidden. Both figures are timed over the *same* work — read Parquet into Arrow, then materialize into the engine's own format — so the columns are directly comparable and the shared Parquet read is charged to every engine.

| single | 311 ms | 147 ms | 174 ms | 1.82 s | 4.34 s |

Server loads include ingest over the client protocol and the work to make rows queryable (ClickHouse `OPTIMIZE ... FINAL`; QuestDB until the WAL is applied).
