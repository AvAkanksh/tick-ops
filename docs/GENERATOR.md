# The market simulator, and why it can be trusted

A benchmark on *inconsistent* data measures nothing, and a correctness check against
data the query itself produced proves nothing. So the simulator is designed around
one property: the three streams it emits are consistent **by construction**, and one
of them is an independent oracle for the query whose correctness matters most.

## What it models

A per-symbol integer-priced limit order book. Each symbol-day, the simulator seeds a
two-sided book around a fair value and then runs a mix of actions — add liquidity,
cancel, and aggressive orders that trade — updating the book and emitting events.

- **`book_events`** records every change to resting size at a level (signed `delta`).
- **`quotes`** records the top of book whenever it changes.
- **`trades`** records one print per level an aggressive order consumes.

Because all three come from the *same* book object in the *same* pass, they cannot
disagree unless there is a bug — which is the point.

## The invariant the whole project leans on

> Replaying `book_events` up to any quote's timestamp reproduces that quote exactly.

This is checked two independent ways:

1. **In `tests/test_generator.py`**, by a pure-Python replay with no query engine
   involved — so the data is validated before DuckDB or pandas ever see it.
2. **In the benchmark itself**, query Q3 reconstructs top-of-book from `book_events`
   alone (never reading `quotes`) at the generator's own quote timestamps, and the
   harness diffs the result against `quotes`. The comparison is a LEFT JOIN *from*
   the distinct quote timestamps, so a timestamp Q3 failed to produce a row for
   counts as a failure rather than being silently dropped — the denominator is the
   true quote count, not the join count. On the committed full dataset this is an
   exact match at **every** quote timestamp (1,048,318 of 1,048,318).

To make "up to a timestamp" unambiguous, every *action* within a symbol is given a
strictly increasing, unique `ts` (the per-symbol clock advances by at least 2 each
action); all book events of one action share it, and the resulting quote is recorded
at `ts + 1` so a trade's "prevailing quote" is the state *before* it, not the quote
its own execution produced. So reconstruction keyed on `ts` is well defined, and a
sweep's several events at one instant still replay in `seq` order.

## Realistic structure, not noise

The data has to *look* like a market or the queries measure nothing interesting:

- **Cross-symbol correlation is real.** Every symbol's fair value tracks a shared
  per-second market factor with a symbol-specific beta plus idiosyncratic noise, so
  pairwise correlation rises with the product of the two betas — a positive but noisy
  relationship (measured Spearman rank correlation ≈ 0.74 between a pair's measured
  correlation and its beta-product on the committed dataset; individual pair rankings
  do get shuffled by the idiosyncratic noise, so this is a trend, not a strict
  ordering). The point is that Q5 measures genuine structure, not white noise.
- **Directional pressure.** When fair value is above mid, adds favor the bid, quote
  improvements lean bid, and aggressors lean buy — so the book drifts and trades
  cluster, rather than being symmetric noise. This gives Q4 (event study) a real
  (small) forward-return signal to find around large trades.
- **The book breathes.** Cancels lean opposite to adds, and a side that empties is
  reseeded, so the top of book churns continuously and Q1/Q3 have a non-trivial
  quote series to join against.

## Determinism

Everything is seeded. Each symbol-day draws from `default_rng([seed, day,
symbol_idx])`, so a symbol-day is independently reproducible and the whole dataset is
bit-reproducible from the seed — the property `test_generator.py` asserts directly.
The three result files are regenerated by three scripts: `results/benchmark.*` by
`scripts/run_bench.py` (which takes `--seed`, default 20260731), and
`results/scaling.*` / `results/partition_study.*` by `scripts/run_scaling.py` and
`scripts/run_partition_study.py` respectively. The latter two use the default seed
baked into `SimConfig`; the timings they report are machine-dependent (the data they
generate is not), so their `meta` blocks record the platform and tool versions.
